# Yiz AI 5.0 — production deployment

## Architecture

Yiz AI 5.0 separates the platform into three runtime layers:

1. **Frontend** — a standalone Nginx web service serving the Yiz AI UI. It proxies `/api/*` to the private API service, including long-lived SSE chat streams.
2. **API** — FastAPI handles authentication, conversations, streaming orchestration, tools, uploads, and lightweight request work.
3. **Worker** — a background process consumes Redis jobs for image/video/audio generation, document generation, charts, and other heavy media work.

Uploaded and generated files use an S3-compatible object store when `MEDIA_STORAGE=s3`. Cloudflare R2, AWS S3, MinIO, Backblaze B2 S3-compatible storage, and similar providers can be used.

The API keeps a small local cache only when an object must be materialized for DuckDB/Pandas analysis. This means the application no longer depends on a persistent application disk for user media.

## Why this is safer to scale

- API instances remain stateless with respect to user files.
- Multiple API instances can share the same Postgres, Redis queue, and object storage.
- Heavy media operations run outside the request-serving API process.
- Each stored object is namespaced by its owner and its metadata is recorded in Postgres.
- `/api/media/...` checks ownership before serving an object.
- Redis-backed jobs have explicit status, timeout, and failure states.
- The frontend and API can be deployed and scaled independently.

## Storage configuration

Set:

```text
MEDIA_STORAGE=s3
S3_ENDPOINT_URL=https://<your-s3-endpoint>
S3_BUCKET=<bucket-name>
S3_REGION=auto
S3_ACCESS_KEY_ID=<access-key>
S3_SECRET_ACCESS_KEY=<secret-key>
S3_PREFIX=yiz-ai
```

For AWS S3, omit `S3_ENDPOINT_URL` and use the appropriate AWS region. For Cloudflare R2, use the account-specific S3 endpoint and `S3_REGION=auto`.

For development, `MEDIA_STORAGE=local` is still supported.

## Render deployment

The included `render.yaml` defines:

- `yiz-frontend` — public Docker web service
- `yiz-api` — private Docker API service
- `yiz-worker` — Docker background worker
- `yiz-redis` — Render Key Value / Redis-compatible queue
- `yiz-postgres` — Render Postgres

Render supports Docker services, private services, background workers, Key Value, and Postgres in a Blueprint. The current Blueprint reference documents `pserv` for private services and `worker` for background workers. Render also supports `fromService` and `fromDatabase` references for wiring services together. See the current Render Blueprint documentation before changing plan sizes or resource settings.

### Required production variables

API:

- `DATABASE_URL` — supplied by the Blueprint
- `REDIS_URL` — supplied by the Blueprint
- `JWT_SECRET` — generated by the Blueprint
- `MEDIA_STORAGE=s3`
- `S3_ENDPOINT_URL`
- `S3_BUCKET`
- `S3_ACCESS_KEY_ID`
- `S3_SECRET_ACCESS_KEY`
- `FRONTEND_URL`
- `ALLOWED_ORIGINS`
- at least one LLM provider/key

Worker:

- `DATABASE_URL`
- `REDIS_URL`
- `JWT_SECRET`
- the same S3 configuration
- provider credentials for any media jobs you want enabled

Frontend:

- `YIZ_API_INTERNAL_URL` is wired automatically to the private API service.

### OAuth

Set `FRONTEND_URL` to the public frontend URL and configure `OAUTH_REDIRECT_BASE` to the URL expected by your OAuth provider. Keep the OAuth callback path aligned with the API routes in `yiz_ai.py`.

### Object storage

Do not use a Render disk as the primary media store in this architecture. Object storage is the durable source of truth; the application disk is only a temporary analysis/cache area.

## Railway

Railway remains usable if preferred. The Docker image now binds Uvicorn to the platform-provided `PORT`, so the original hard-coded-port failure is removed. If you keep Railway, provision Redis and an S3-compatible object store and run the worker as a separate service using:

```text
python worker.py
```

The API service continues to use the normal Docker command.

## Production verification checklist

1. `GET /api/health` returns 200 from the API service.
2. Frontend loads and `/api/health` works through the frontend proxy.
3. Registration and login work.
4. Chat streams continuously through SSE.
5. Image/document generation creates a worker job and returns its result.
6. Uploaded files are stored in the configured bucket.
7. A different account cannot fetch another user's object key.
8. Data analysis can materialize an object from S3 into the temporary cache.
9. A worker restart does not corrupt the API process.
10. A redeploy does not remove uploaded/generated media.
11. OAuth callbacks return to the configured frontend domain.
12. Postgres backups and object-store lifecycle/retention policies are configured.

No deployment should be declared production-ready solely from static inspection; the final verification must use the actual production database, Redis, object store, OAuth configuration, and provider credentials.

## Production object storage: Cloudflare R2

For production, use a private Cloudflare R2 bucket such as `yiz-ai-production`.
R2 exposes an S3-compatible API, so YIZ AI uses boto3 without a provider-specific SDK.

Set these variables on both `yiz-api` and `yiz-worker`:

```env
MEDIA_STORAGE=s3
S3_ENDPOINT_URL=https://<ACCOUNT_ID>.r2.cloudflarestorage.com
S3_BUCKET=yiz-ai-production
S3_REGION=auto
S3_ACCESS_KEY_ID=<R2_ACCESS_KEY_ID>
S3_SECRET_ACCESS_KEY=<R2_SECRET_ACCESS_KEY>
S3_PREFIX=yiz-ai
MEDIA_CACHE_DIR=/tmp/yiz-ai-media-cache
```

Create the R2 API token with the narrowest scope possible: Object Read & Write on the YIZ AI production bucket only. Keep the bucket private and never expose the access key or secret to the browser.

Render environment groups are recommended so the same storage configuration can be linked to the API and worker services without copying secrets into source control.

A verification utility is included:

```bash
python scripts/check_s3_storage.py
```

It writes, reads, verifies, and deletes a temporary object, proving the configured endpoint and credentials have working object read/write access.
